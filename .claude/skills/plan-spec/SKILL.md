# Plan-Spec：需求规格评审

## 概述

和用户一起过需求，确保双方理解一致，产出一份结构化 Spec 文档作为后续拆分（plan-breakdown）的输入。

**核心原则：** 标准前置。写代码之前先把「要做什么、不做什么、做到什么程度」说清楚，避免后期返工。

## 何时使用（先按任务规模分档，别一刀切走满流程）

先判断任务规模，选对应仪式——轻任务不背重流程，重任务不能偷工。**每一档都要停下来等用户确认边界再动手**：

| 档 | 判据 | 走多重的流程 |
|---|---|---|
| spike | 探索/极小改动：改文案、修单个 bug、试探性验证 | 跳过 Spec，直接做，只用一句话标注意图与影响范围 |
| bounded | 单个有界功能，边界基本清楚 | 轻量 Spec：一句话描述 + 边界条件 + P0 验收总纲，跳过完整追问仪式 |
| architectural | 架构级/多能力/影响面大/有明显取舍 | 完整流程（下方）+ 多能力先出 Spec 地图 |

拿不准就往高一档走。对齐 Superpowers v6.3.0「按任务规模分流」：小任务跳过重仪式，但每条路径都停下等用户批准再实现。

**已有清晰 Spec** → 直接用 plan-breakdown 拆分，不重复走本 skill。

以下流程是 architectural 档的完整版；bounded 档按需裁剪（只做理解目标 + 边界追问 + P0 总纲）。要做 Agent 时，bounded 也要写「Agent 方案」，只是每项可以短。

## 流程

1. **理解目标** — 让用户用自然语言说清：做什么、给谁用、核心功能有哪些。
2. **先定 Spec 结构，再写内容** — 判断这是单一能力还是多能力项目，决定写一份还是一组 Spec。见下方「Spec 分解」。**这一步不能跳过**：分解要在动笔前做，不是等写不下去了才补救。
3. **像产品经理一样追问** — 一次问一个问题，聚焦三类边界（多 Spec 时对每份各做一遍）。复述已理解的部分时，用户说过的和模型猜测的分开写，猜测标成「猜测」：
   - 边界条件：什么明确不在范围内
   - 异常场景：出错/极端输入怎么处理
   - 非功能性需求：性能、安全、可维护性
4. **设计用户使用路径（面向终端用户 UI 的产品才做）** — 见下方「用户使用路径与信息架构」。没有终端界面的后端/库/CLI 跳过本步；它是 Agent 时，调用与错误路径写在「Agent 方案」里。
5. **定 Agent 方案（会调用模型，并且多步执行、调工具、跨轮保留信息或回答依赖外部资料时才做）** — 读 `reference/agent-design-guide.md`，把决定写进同一份 Spec 的「Agent 方案」。单轮、无工具、不查外部资料的功能整节写「不需要」。详见下方「Agent 方案」。
6. **确认技术约束** — 语言、框架、部署环境、已有技术栈是否必须沿用。用户没表态的平台、语言、库写成「模型建议，待确认」，不得写成用户已同意。框架选定并冻结后，再把该版本的官方编程资料引进项目，不写进 Spec 正文。
7. **定义接口契约（若产出要被他人/他系统调用）** — 见下方「接口契约三问」。
8. **产出结构化 Spec** — 按模板填写，逐项与用户确认；初始 `status: Draft`。
9. **冻结** — 先按「实现者视角」过一遍（见下方），再由用户确认，然后把 `status` 改为 `Frozen`；有 `INDEX.md` 就同步登记（多份 Spec 时必须有）。还有「只有用户能答、且会改变产物」的问题则保持 Draft。需要 Agent 方案却没写、也没写「不需要」的，不得冻结。
10. **交接** — Spec 冻结后，提示进入 plan-breakdown 做任务拆分。

## Spec 分解（第 2 步展开）

**先看项目里有没有 `docs/spec/`：**

| 情况 | 怎么做 |
|---|---|
| 没有（新项目） | 走下面的「几个能力」判断 |
| 已有（增量需求） | 先读 `INDEX.md`（还没建就直接看 `docs/spec/` 下已有的 Spec），再按下面的「增量需求怎么挂」定位 |

### 新项目：先问几个能力

**这个需求里有几个「用户能独立感知、且能独立上线」的能力？**

| 回答 | 怎么写 |
|---|---|
| 一个 | 写一份 Spec，直接进第 3 步 |
| 多个 | 先出 **Spec 地图**，再逐个写子 Spec |

### 增量需求怎么挂

读完 `INDEX.md` 后判断这次的需求落在哪：

| 判断 | 动作 |
|---|---|
| 是一个新的独立能力 | 新建子 Spec，`parent` 写现有项目级 Spec；若原来没有项目级 Spec（原本是单一能力项目），先补一份 `PROJECT.md` 把原 Spec 挂上去，并建 `INDEX.md`（此时已有两份以上） |
| 是对现有能力的语义变更（范围/验收/优先级变了） | 走 revision：新建版本，旧版标 `superseded_by`，见「Spec 生命周期」 |
| 只是现有 Spec 的补充说明、错别字、链接失效 | 原地改，不用新 Spec |

**不要**因为「有新需求」就无脑新建一份平级 Spec——先确认它跟现有哪份的边界不重叠。

### Spec 地图怎么出

多能力项目的第一份产出，写在项目级 Spec 里：

1. 列出各个能力，一个能力一份子 Spec，先只写标题与一句话描述
2. 项目级 Spec 只保留**跨子 Spec 的不变量**：全局边界、共享的非功能性需求、统一的技术约束、子 Spec 清单
3. 与用户确认这张地图，再按优先级逐个展开子 Spec（不要一次全展开，只细化最近要做的 1-2 个）
4. 每份子 Spec 的 front matter 写 `parent: <项目级 spec_id>`，并登记 `docs/spec/INDEX.md`

### 按什么拆（拆分依据）

| 依据 | 判据 |
|---|---|
| 用户可独立感知的能力 | 能不能对用户单独描述「这个功能是什么」 |
| 可独立上线的单元 | 能不能单独发布而不破坏其他部分 |
| 验收互不交叉 | 一份 Spec 的验收项是不是一组相关的、能一起验完的 |

**不要按这些拆**：代码模块划分（实现细节不该反向决定需求边界）、开发排期、字数。

**兜底信号**（不是拆分依据，只是提醒你可能漏拆了）：一份 Spec 正文超过约 500 字，或核心功能超过 7 条，或出现两组互不相干的验收标准 —— 回头重看上面三条判据。

### 编号怎么取

- `spec_id`：新建前看 `INDEX.md` 现有最大号 +1；没有 INDEX 就从 `SPEC-001` 起。**编号只增不复用**，即使 Spec 被 Superseded。
- AC 编号：**在单份 Spec 内唯一**即可（每份都可以从 `AC-001` 起）。跨 Spec 引用时必须带 spec_id，写成 `SPEC-002/AC-001`；Issue 里已用 `spec:` 声明了归属的，`accepts:` 可只写 `AC-001`。

## 证据合同（P0/P1 验收项前置）

Spec 里的 P0/P1 验收项，凡是「结论算不算数取决于外部证据」的（法源核验、外部 connector、模型质量、端到端功能不回退），在 AC 旁标注它的**真源**与**失败关闭终态**，别把「模型说已核验 / 有候选链接 / 接口能返回 JSON」当成通过。

- 轻量做法：AC 表增补一列证据等级（E0 自动可复现 / E1 人工确认 / E2 外部待核验 / E3 推断），E2/E3 不得作为「已验收」。
- 完整做法：拆 Issue 时按 `templates/evidence-contract-template.md` 为该结论挂证据合同（`source_of_truth` / `required_fields` / `fail_closed_state`），规则见 plan-breakdown。
- 冻结判断：一份 Spec 的 P0/P1 AC 只有拿到与其证据等级相符的证据才转 `Verified`；停在 E2/E3 的维持 `Frozen`。

## 接口契约三问（条件触发）

若本需求的产出会被其他人、前端或外部系统调用，Spec 中必须回答三问：

1. **输入是什么** — 字段名、类型、必填/可选。
2. **输出是什么** — 正常返回什么；出错返回什么（4xx = 调用方的错，5xx = 服务方的错）。
3. **怎么调用** — HTTP / gRPC / 消息队列 / MCP 等。

约定：

- **载体用行业标准**，不自创规范：HTTP 用 OpenAPI（自动文档），字段校验用类型化 Schema（Pydantic / zod / struct tag 等各语言对位物）。
- **契约一经发布不改**，要变就加版本（`/v1` → `/v2`），旧调用方继续可用。
- 契约是语言/框架无关的承诺：调用方不需要知道内部用什么实现。

## 用户使用路径与信息架构（面向终端用户 UI 的产品才做）

没有终端界面的后端/库/CLI 跳过本节（是 Agent 的，调用与错误路径写在「Agent 方案」）。凡是有终端用户界面的产品，功能怎么实现之外还要先设计「用户怎么用」——否则界面主次错位（如核心问答被对话记录挤在一起）会拖到测试期才暴露。按任务三档：spike 跳过，bounded/architectural 都要。Spec 冻结前回答：

- **核心任务主线**：用户来做的最核心一件事是什么？主界面必须为它让出主焦点。
- **关键路径步骤**：从入口到完成这件事的最短步骤序列（入口 → … → 完成），标出高频动作。
- **主/次信息布局**：哪些是主内容（占主界面），哪些是辅助/历史/设置/日志（进侧栏、二级页或折叠）。反例自检：不要让次要信息（对话记录、历史列表、配置）挤占核心任务的主界面焦点。
- **与验收挂钩**：把关键路径写成可验收的端到端场景，对应 P0 AC 的「用户可完成路径」。

**硬规则：** 有 UI 的产品，Spec 里没有「核心任务主线 + 主/次信息布局」不得冻结。布局主次是产品决策，要停下等用户确认，别默认堆在一屏。

## Agent 方案（要做 Agent 时才写，与功能写在同一份 Spec）

要做的东西会调用模型，并且会多步执行、调工具、跨轮保留信息，或回答依赖外部资料（知识库/检索，哪怕只检索一次）时，冻结前读 `reference/agent-design-guide.md`，在 Spec 里写完这些项：控制方式、谁做决定、工具与业务技能、上下文与记忆、知识库与召回、运行边界、用户/调用方路径。每一项写选什么、为什么不选旁边那个；不需要就写「不需要」。答案依赖外部资料时，「知识库与召回」不能空着：业务库存哪、是否用向量库、按什么切、先精确匹配还是先检索。没有知识库就写「不需要」。

单轮、无工具、不查外部资料的功能整节写「不需要 Agent 方案」，不要删掉这一节。控制方式或记忆语义变了，走现有 revision，不另存一份方案。编程用的官方 Skill 在框架选定并冻结之后引进项目，不写进 Spec 正文，也不能代替业务 Agent 运行时的工具。

## 能力矩阵（防范围后置暴露）

需求描述、原型和「已验证能力」之间要在每次外部评测/验收后立即维护一张矩阵，否则范围问题会以「实现缺口」的形式在项目末期才被迫收口（真实教训：从 DOCX-only 到 DOCX+文本 PDF、从泛合同到特定合同+特定立场，都是后期才冻结）。

每份 Spec 维护一张能力矩阵，每一类（输入格式、输出格式、立场/角色、子能力）都必须是四选一：

```yaml
capability_matrix:
  - capability: "输入格式 / 立场 / 子能力 ……"
    status: "verified | planned | unsupported | pending_external"
    spec_revision: "SPEC-xxx"
    test_fixture: "path 或 null"
    blind_set: "path 或 null"
    owner_confirmation: "回执路径 或 null"
```

- `verified`：有与证据等级相符的通过证据；`planned`：计划做但未实现——**实现任务不得把 `planned` 写成 `verified`**。
- `unsupported`：明确不做，必须有**用户可见的失败原因 + 替代路径**。
- `pending_external`：等外部条件（供应商条款、盲测、部署），必须有责任人。

## 冻结前：换实现者视角看一遍

冻结前把 Spec 当成即将来实现的人读一遍，问题分成三堆。不要为此再派子代理。

- **对话里已经回答的**：写进 Spec。
- **实现者可以自己定、且不改变做什么的**：自己定，并标明这是模型的决定，不是用户同意的。
- **只有用户能答、且答案会改变产物的**：一次问完。还有这一堆，不得 Frozen。

## 范围变更协议

- 已 `Frozen` 的 Spec **不在原文件语义改写**；输入格式、立场、合同/业务类型、发布边界任一改变，都新建 revision（旧版转 Superseded），见「Spec 生命周期」。
- 「用户确认了范围」只改变 `scope`（矩阵条目增减/状态），**不能把实现状态直接变成 `verified`**——范围确认 ≠ 功能已验收。

## Spec 生命周期（四态）

每份 Spec 在 front matter 标 `status`，状态决定能做什么。**每个状态都有明确的置位人**，否则状态就是摆设：

| 状态 | 含义 | 允许的动作 | 谁置位 |
|---|---|---|---|
| Draft | 还在澄清 | 自由编辑；**不能**作为实施或验收完成的依据 | plan-spec 新建时 |
| Frozen | 范围、验收、优先级已确认 | 可以拆 Issue、进入实施 | plan-spec，用户确认后 |
| Verified | P0/P1 验收项都有通过证据 | 可作为交付依据 | verify-review，本 Spec 的 P0/P1 AC 全部通过时回写 |
| Superseded | 已被新版本取代 | 只读，必须指向后继 Spec | plan-spec，新建 revision 时 |

**注意 Verified 是 Spec 级而非 Issue 级**：一份 Spec 通常被拆成多个 Issue，最后一个 Issue 的 review 通过时才检查整份 Spec 能否转 Verified；有 AC 处于 blocked 的不能转。

`status` 的真源是各 Spec 自己的 front matter，`INDEX.md` 是它的镜像——改状态时两处一起改。项目级 Spec 的子 Spec 清单**不记 status**，避免第三处漂移。

**冻结后怎么改：** 冻结后的语义变更（范围、验收、优先级）不要原地改，新建一份 revision，旧版保持只读并标 `superseded_by`。写清变更原因与受影响的验收项。错别字、链接失效这类修正可以原地改。

## 目录布局

单一能力项目：

```
docs/spec/
  <feature>.md        # 只有一份 Spec 时不必建 INDEX.md
```

出现第二份 Spec 时再补 `INDEX.md`，把已有那份一并登记。

多能力项目：

```
docs/spec/
  INDEX.md
  PROJECT.md          # 项目级 Spec：跨子 Spec 的不变量 + 子 Spec 清单
  <feature-a>.md      # parent: 项目级 spec_id
  <feature-b>.md      # parent: 项目级 spec_id
```

`PLAN.md` 只挂当前活跃的 Spec 链接，全量目录在 `INDEX.md`——别让 PLAN 承担 Spec 目录职责。

## 产出

用 `templates/spec-template.md`，篇幅以说清边界为准。**两种 Spec 各写各的，不要重复**：

| | 项目级 Spec（多能力项目才有） | 子 Spec / 单一能力 Spec |
|---|---|---|
| 一句话描述 | 整个项目是什么、给谁用 | 这个能力是什么 |
| 核心功能 | 不写，改列子 Spec 清单 | 本能力的功能列表 |
| 边界条件 | 整个项目明确不做的 | 本能力不做的 |
| 非功能性需求 | 全局共享的 | 仅本能力特有的 |
| 技术约束 | 全局统一的 | 仅本能力特有的 |
| 接口契约 | 不写 | 若本能力对外交付则写 |
| 验收标准 | 项目级 P0 总纲 | 本能力的 AC（可编号） |

子 Spec 不要复制项目级已声明的全局约束，写一句「继承 `parent` 的全局约束」即可。

保存到 `docs/spec/`；有 `INDEX.md` 就登记一行。

## 提示词参考

> 我想做一个【XXX】。先判断这里面有几个用户能独立感知、且能独立上线的能力：只有一个就写一份 Spec；有多个就先给我一张 Spec 地图（项目级 Spec + 子 Spec 清单，每个只写标题和一句话），我确认后再逐个展开。
>
> 展开某份 Spec 时，像产品经理一样向我提问（一次一个问题），澄清需求边界、异常场景和非功能性需求，然后输出结构化 Spec：一句话描述、核心功能、边界条件、非功能性需求、技术约束、P0 验收总纲。

## 常见错误

- **跳过追问直接写 Spec** → Spec 反映的是你的假设而非用户真实意图。必须先问后写。
- **一次抛一堆问题** → 用户难以回答。一次问一个，逐步收敛。
- **把 Spec 写成需求清单堆砌** → 缺「边界条件」和「不做什么」，后期范围蔓延。边界必须显式写。
- **多能力项目硬塞一份 Spec** → 边界互相污染，改一处牵动全篇。动笔前先走第 2 步分解，出 Spec 地图。
- **写不下去了才想起拆** → 已经写歪的边界会被继承进子 Spec。分解是前置动作，不是补救动作。
- **一次把所有子 Spec 全写细** → 后面的需求还会变，细化都白做。地图确认后只细化最近要做的 1-2 个。
- **按代码模块拆 Spec** → 实现细节反向决定了需求边界。按「用户可独立感知 + 可独立上线 + 验收不交叉」拆。
- **子 Spec 复制粘贴项目级约束** → 全局约束改一次要改 N 份，迟早不一致。子 Spec 写「继承 parent」。
- **产出要对外交付却没定契约** → 实现完再补契约，接口形状会被内部实现牵着走。契约必须在 Spec 阶段定。
- **有 UI 却只想「怎么实现」不想「用户怎么用」** → 次要信息（历史/设置）堆在核心任务主界面，用户找不到核心功能，拖到测试期才发现。Spec 阶段先定核心主线与主/次布局。
- **Draft 就开工** → 边写边改需求，实现被牵着走。拆 Issue 前先把 Spec 冻结（Frozen）。
- **冻结后原地改语义** → 已按旧版实施的 Issue 失去依据。语义变更要新建 revision，旧版标 Superseded。
- **子 Spec 不写 parent** → 散成互不相认的碎片，看不出全貌。子 Spec 必须挂在父 Spec 下并登记 INDEX。
- **增量需求不看已有 Spec 就新建** → 新 Spec 与现有那份边界重叠，两边验收互相打架。先读 `INDEX.md` 再定位是新子 Spec、revision 还是原地改。
- **每份 Spec 都从 SPEC-001 起** → 编号撞车，Issue 的 `spec:` 指向不明。新建前查 INDEX 取最大号 +1。
- **改了状态只改一处** → Spec front matter 与 INDEX 对不上，看目录以为还没冻结。两处一起改。
- **模型选的技术栈写成用户已同意** → 用户没表态就标「模型建议，待确认」。
- **复述时把猜测写成用户原话** → 猜测单独标出。
- **还有会改变产物的问题就 Frozen** → 先用实现者视角分三堆，第三堆问完再冻结。
- **Agent 产品只写了功能就冻结** → 控制方式、记忆和调用路径还没定。先写「Agent 方案」，或明确写不需要。
