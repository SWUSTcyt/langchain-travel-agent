# UI / 前端工作指南（有终端界面时按需读）

> 给 `plan-spec`、`plan-breakdown`、`verify-test` 用。要做的东西有用户直接操作的界面（Web、桌面、移动端）时才读；纯后端、库、命令行不读。
> 从零开发的新项目和已有项目的改版都适用。不预设技术栈：由 Agent 按第 2 节推荐，用户确认后才算定。

## 1. 原型评审（Spec 冻结前）

布局有取舍时，文字描述不够用户选。先交可点击原型，确认后再写产品代码。不涉及布局取舍的小改动（改文案、调间距、修单个样式）不做原型。

- **一个入口**：每轮只给一个入口文件，页面上写版本号（如 v0.3），并列出其余文件各是什么。不要让用户自己判断两个相似文件哪个是方案。
- **同条件对比**：有新旧或多个方案时，放在同一宽度、同一场景下对比，不要让响应式布局掩盖差异。
- **四种状态**：正常、空、加载、失败都能切到；会出现「证据不足」「无权限」这类业务状态的，也要能切到。
- **演示数据**：原型不连真实接口，页面上标明是演示数据。原型能点，不代表业务能力已经实现。
- **按位置复述**：用户对布局提意见后，先用「哪个页面、哪个位置、哪个控件、改什么、不改什么」复述一遍，再动手。一句「删掉上面那个」很容易被扩大成重做整套导航。
- **记录确认**：写进 Spec 的确认要有：版本、确认了哪些页面和交互、用户原话、日期，以及没展示的页面（登录、设置、异常页）怎么继承已确认的样式。

原型确认只冻结视觉和交互，不改变能力矩阵里任何一项的实现状态。

## 2. 前端技术方案（原型确认后、Spec 冻结前，推荐给用户确认）

原型确认后、拆任务前，Agent 推荐一套前端技术方案，写进 Spec「技术约束」，每项标「模型建议，待确认」，用户确认后才算定。新项目由 Agent 给推荐；已有项目默认沿用现有技术栈，要换必须写清理由和代价，并单独确认。

每项写：选什么、为什么、代价、没选什么。

- **框架、语言、构建**：用什么框架，要不要类型检查，用什么构建工具。
- **分层**：页面、可复用组件、业务状态、接口客户端各放在哪里，谁可以调用谁。
- **状态归属**：哪些来自服务端（列表、详情、权限结果），哪些只是界面状态（展开、选中、未提交的草稿）；登录会话怎么恢复、过期怎么处理。
- **接口**：前端按什么契约调用后端；返回数据要不要在运行时校验；失败、超时、无权限在界面上分别怎么显示。
- **权限**：后端是权限真源，前端只按后端结果显示或隐藏，不自己判断能不能做。
- **样式**：把已确认原型的颜色、字号、间距抽成共享变量，后续页面直接继承；响应式用断点还是弹性布局。
- **测试工具**：单元/组件测试、浏览器测试各用什么，哪些进 CI。
- **怎么发布**：构建产物由谁提供（后端托管静态文件、独立静态服务、CDN）。这决定第 3 节的「真实入口」是哪个地址。

不要只因为「主流」就选重框架。页面少、交互简单时，写明为什么不用更轻的方案。

## 3. 在真实产品入口验收

设计预览常常带展示外框、固定宽度或演示数据，在预览里看起来正常，不代表产品页面正常。视觉和交互验收的对象是用户真实打开的入口：产品构建产物，按部署方式启动；不是设计预览，也不是开发服务器。

每条关键路径至少走这几类视口：

| 视口 | 示例尺寸 | 重点看 |
|---|---|---|
| 宽屏 | 1920×1080、2560×1440 | 主内容是否随宽度变宽，不缩在中间一小块 |
| 常规桌面 | 1366×768、1024×768 | 侧栏、主内容、操作按钮都在可见区域内 |
| 窄屏 | 390×844 | 没有横向溢出，导航和账户入口仍能点到 |
| 短视口 | 390×420 或 1366×600 | 内容可滚动，固定的页头页脚不遮挡表单和按钮 |

再加两类内容：很长的列表或历史（几百条），很长的正文（几百行）。不同角色（如普通用户和管理员）看到的导航不同时，每个角色各走一遍。

除了布局，还要在产品入口上验真实状态：接口失败、超时、空数据、无权限时，界面显示的是原型里确认过的那几种状态，而不是空白页或无限加载。键盘能走通关键路径，控件有可读的名称。

## 4. 哪些能自动查，哪些要人看

可以自动断言：是否有横向溢出；主内容区域的矩形尺寸和占可用宽度的比例；长内容能否滚到底；关键控件能否点击、点击后是否到达预期页面；接口失败、空数据时是否显示对应状态；键盘焦点能否到达关键控件、控件是否有可读名称（可用无障碍检查工具）；页脚等固定信息出现的次数；每个视口留一张截图。

需要人判断：主次是否合理；比例和留白是否舒服；文案和标题是否重复表达；与已确认原型「看起来是不是同一个东西」。自动检查全过，只能说明没有明显的布局缺陷，不代表视觉验收通过。

## 5. 浏览器测试装置

- **等应用就绪**：等应用自己给出的就绪信号（如账户入口变为可点击、首屏数据渲染完成），不用页面 load 或 `document.readyState === "complete"` 代替。页面加载完成时，应用往往还在初始化会话。
- **先分诊再改代码**：测试失败时，先判断是装置问题（选择器错、等待条件不对、注入存储与应用初始化抢跑、iframe 没定位到）还是产品问题。办法是在同一入口手动复现，或换成就绪信号再跑一次。装置问题只改测试，不改产品代码，也不记成产品缺陷。
- **选择器选可见可用的控件**：断言用户真正能看到、能点的元素，不断言隐藏元素或演示用的占位按钮。

## 6. 测试创建的登录凭据

在真实或共享环境跑浏览器测试时，测试自己登录产生的会话凭据要能撤销：

- 测试进程在内存里保留撤销所需的凭据或会话标识，不依赖浏览器存储（应用初始化可能会清掉它）。
- 在 finally 里调用退出或撤销接口；正常结束、断言失败、超时都要走到。
- 跑完后按服务端的签发记录核对：本轮测试账号还有没有未撤销的会话。有残留就只撤销本轮的，不影响其他用户。
- 浏览器 profile 可能已经把凭据写进磁盘，不要声称「从未落盘」；profile 目录按敏感材料保管或删除。

## 7. 性能结论口径

换框架不等于变快。要写性能结论时，写明：对比的两个版本、同一设备、浏览器、网络和视口；冷缓存和热缓存分组；每组样本数；失败样本是否保留；样本绑定的构建产物版本。旧样本不能代表后来上线的包。维护性收益和性能结论分开写。

## 交给后续流程

- `plan-breakdown`：按用户路径拆 Milestone。新项目的第一个 Milestone 就交付一条能真实走通的路径（真实接口、真实入口），不要先把所有页面做成静态壳、最后再统一接接口；之后每个 Milestone 多走通一条（见 Milestone 模板「用户使用路径增量」）。改版或迁移同样按路径逐条切换，每条对照已确认原型。
- `verify-test`：关键路径的视口和内容检查写进测试计划，并标出哪些是自动、哪些是人工。
- PR 摘要：每项检查写运行位置（CI、仅本地、未跑）。前端测试、类型检查、产品构建没进 CI 时，写「仅本地」。
- 用户在产品页面里发现、而门禁没发现的视觉问题，在会话摘要里单独记一条，作为下次补检查的依据。
