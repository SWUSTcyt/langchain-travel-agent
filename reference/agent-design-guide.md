# 业务 Agent 方案（Spec 冻结前按需读）

> 给 `plan-spec` 用。要做的东西会调用模型，并且会多步执行、调工具、跨轮保留信息，或回答依赖外部资料时才读。
> 决定写进同一份 Spec 的「Agent 方案」，不另开一篇。单轮、无工具、不查外部资料：整节写「不需要」，不要删节。
> 每一项都写：选什么、为什么不选旁边那个。不需要的项写「不需要」，不要留空。

框架官方文档和编程 Skill 不写进 Spec。框架选定并冻结之后，再按该版本引进项目。编程资料只帮助写代码，不能代替业务 Agent 运行时要调用的工具。

## 1. 控制方式

先定请求怎么往下走，再谈记忆和界面。五选一（或写明组合里谁是主路径）：

| 方式 | 适用 | 不要用在 |
|---|---|---|
| 一次请求 | 问完即答，无工具、无分支 | 需要查资料或连续改条件 |
| 固定分支 | 步骤和条件能事先写死 | 下一步取决于上一步工具结果、分支爆炸 |
| ReAct（边想边调工具） | 工具不多，每步结果决定下一步 | 步骤固定、或循环停不下来会伤用户 |
| 先规划再执行 | 任务长、步骤要先给人看 | 一步就能做完 |
| 多 Agent 分发回收 | 能力必须拆开、各自验收 | 一个角色能做完；不要为了「像 Agent」而拆 |

## 2. 谁做决定

列出哪些步骤由程序写死，哪些交给模型。工具失败、循环是否停止、高风险字段（金额、权限、对外写入）由宿主定，不让模型自己宣布完成或自行升成已核验。

## 3. 工具与业务技能

写出业务 Agent 运行时有哪些工具、怎么选、结果怎么校验。没有就写「不需要工具」。

和「用来写这个框架代码的官方 Skill」分开。后者等框架在技术约束里定稿后，按该版本引进当前项目，不预置进 playbook，也不把第三方合集称作官方。

## 4. 上下文与记忆

先列出必须跨轮留下的信息，再选存储，不要先套一套记忆架构。

| 手段 | 什么时候要 | 什么时候不要 |
|---|---|---|
| 近期窗口 | 刚才几轮还影响当前这句 | 窗口外的约束仍必须生效 |
| 结构化状态 | 预算、所选对象、阶段等字段要被下一步使用 | 每次只有一句、没有要更新的字段 |
| 摘要 | 对话长，但有效约束必须留下 | 用状态或回读原文就能定位 |
| 用到再查 | 事实在资料或记录里，不在对话里 | 用户说的是「刚才那一个」，检索对不上身份 |

若选了摘要，写清：何时压、压哪一段、保留哪些约束和未决项、失败时旧内容是否还在。字符数不要当成 token。

若选了状态，写清：字段如何新增、覆盖、移除；依赖它的下一步必须使用更新后的值。例如用户改了筛选条件后，下一次查询用新条件，而不是上一轮的结果。

历史回答默认不能当作当前事实，除非方案写明可以，并写出来源。

## 5. 知识库与召回

回答要依赖一份资料（法规、文档、商品库、内部记录）时才写。宿主程序先检索、再交给模型答一次，也算。没有外部资料，写「不需要知识库」。

先定事实放在哪，再决定要不要向量库：

- **业务库**：权威记录放在哪（关系数据库、对象存储等）。这是事实的真源；搜索引擎和向量库只是索引，可以从业务库重建。
- **要不要向量库**：只有「没有稳定编号、靠语义才能找到」时才用。有条号、单号、主键时，先精确匹配，匹配不到就失败关闭，不用向量或关键词去凑一条像的。
- **用哪一个**：写出产品名和版本，以及为什么不用另一个。没验证过的写成「待验证」，不能写成已经可用。
- **怎么切**：按什么单位切（条、节、页、固定长度）、重叠多少、每片带什么元数据（来源、版本、条号、权限范围）。切分方式变了，就是方案变更。
- **怎么召回**：先精确还是先检索、取多少条、权限怎么滤。召回结果是候选，不是已核验事实。Top-K 不能用来证明「资料里全部相关内容都找到了」。找不到或来源不可读时，不得改由模型凭记忆作答。

实现时的失败关闭和证据资格见 `reference/model-and-connector-guide.md`。这里只定选择，不写切分代码。

## 6. 运行边界

外部写入、沙箱、长任务能否停下再继续、要不要运行追踪和评测门禁。用不到的写「不做」。对外写入必须有确认和结果反馈；只读查询不要加无意义的确认。

## 7. 用户 / 调用方路径

沿着上面的设计走一遍：信息够就继续；有歧义只问必要的问题；改了条件这一轮就生效；执行中能否看见进度；失败后已填内容还在不在。

有界面时，主次布局仍写在 Spec 的「用户使用路径与信息架构」。无界面的 API/CLI 把调用和错误路径写在本项，不必为此做页面。

## 交给后续流程

`plan-breakdown` 拆 Issue 时，每条实现任务和「合理用户会踩」的测试都要能指回上面某一项。方案写了不需要的能力，不拆对应的实现任务。控制方式、记忆语义或切分/召回方式变了，改 Spec 的 revision，不另写一份方案。
