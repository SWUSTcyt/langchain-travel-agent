# 前端技术方案比较（SPEC-004 附件）

> 状态：2026-10-20 用户确认方案 A（Gradio 内嵌高德 JS）。已写入 SPEC-004「技术约束」。
> 依据：`reference/ui-frontend-guide.md` 第 2 节。已有项目默认沿用现有栈，换栈需单独确认。

## 现状

- 界面是 Gradio 6（[ui.py](../../ui.py)），`python main.py` 本地启动。
- 回答用 `agent.stream` 流式产出，思考过程和最终答案分开显示。
- 会话状态由每轮的 Gradio 历史算出（[turn_context.py](../../turn_context.py)），随请求以 `context=` 传给中间件。

## 方案 A：继续用 Gradio，地图用高德 JS 嵌入

| 项 | 做法 |
|---|---|
| 框架 | Gradio 6 `gr.Blocks`；左栏 `gr.HTML` 渲染文字行程，右栏 `gr.HTML` 放高德地图容器，`head=` 注入高德 JS |
| 分层 | `ui.py` 只负责布局与事件；结构化行程转成 HTML 的逻辑放新模块（如 `itinerary_view.py`），可单测 |
| 状态 | 会话历史仍在 `gr.State` / Chatbot；结构化行程放 `gr.State`，每轮更新 |
| 接口 | 同进程调用 `agent.stream`，不新增 HTTP 接口 |
| 地图交互 | 点天数、点地点在浏览器里用 JS 完成；Python 侧只把整份行程 JSON 写进页面 |
| 样式 | 继续用 `assets/custom.css`，把 v0.11 的颜色、字号、间距抽成变量 |
| 测试 | 现有 unittest；页面用浏览器在 `python main.py` 启动的真实入口上验收 |
| 发布 | 不变：`python main.py` |

- 理由：改动最小，流式回答、思考过程、会话状态全都沿用；单人本地项目够用。
- 代价：Gradio 对自定义 JS 的支持较绕，点击地图和文字联动要写在注入脚本里；外观受 Gradio 组件约束，Stitch 稿可能要打折扣。

## 方案 B：Python 只提供接口，前端改成独立静态页

| 项 | 做法 |
|---|---|
| 框架 | 后端 FastAPI 提供流式接口（SSE）；前端 Vite + 原生 TypeScript 或 Vue |
| 分层 | 前端：页面 / 行程组件 / 地图组件 / 接口客户端；后端：接口层不做业务判断，调用现有 agent |
| 状态 | 会话历史改由前端保存并随请求发送；后端无状态 |
| 接口 | 新定义 `/v1/chat` 契约（输入：历史与本句；输出：流式事件 + 最终结构化行程） |
| 测试 | 后端加接口测试；前端加组件测试和浏览器测试 |
| 发布 | 后端托管构建好的静态文件，仍可一条命令启动 |

- 理由：能完全照 Stitch 稿实现，地图与文字联动最自然。
- 代价：新增一套前端工程和接口契约；`ui.py` 的流式逻辑要重写成 SSE；测试量翻倍。违反「已有项目默认沿用现有栈」，需要你单独确认。

## 推荐

先用方案 A 打通第一条真实路径（成都三天：文字 + 标点 + 第 1 天路线）。若 Stitch 稿在 Gradio 里实现不了，或者地图与文字联动太别扭，再按方案 B 单独立项。没选 B 作为起点的原因：现在只有一个页面、一个用户，独立前端工程的维护成本大于收益；已有项目默认沿用现有栈。

外观先按 Stitch 稿在方案 A 里尽量贴近。若 Gradio 组件把布局或样式压得走样，再单独立项换方案 B。用户之前说过现有 Gradio 页面丑，那是对旧布局的评价，不等于已经选定独立前端。

## 两件必须写清的事

- 高德 Web 端 JS 需要单独申请「Web 端（JS API）」key 和安全密钥，存环境变量（如 `AMAP_JS_KEY`、`AMAP_JS_SECURITY_CODE`），不进仓库；与 `AMAP_MCP_URL` 分开。缺少时地图区显示「地图暂不可用」，文字照常。
- 流式思考过程和会话状态：方案 A 下沿用 `stream_answer` 与 `turn_context.py`，只在最终答案后额外产出结构化行程；方案 B 下要把同样的事件搬到 SSE。
